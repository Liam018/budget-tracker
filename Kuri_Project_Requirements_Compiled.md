📅 Bill due: Your ₱1,500 PLDT Internet bill is due in 24 hours.

\`\`\`



**### PWA Web Push Notification Architecture**



\| Component | Responsibility |

\|---|---|

\| **\*\*Frontend PWA Hook (\`useWebPush\`)\*\*** | Prompts for permission via \`Notification.requestPermission()\`, creates subscription via \`registration.pushManager.subscribe({ userVisibleOnly: true, applicationServerKey })\`. |

\| **\*\*VAPID Keys\*\*** | Standard public/private VAPID keypair identifying the application server to push services (Apple Push Notification service and Google FCM). |

\| **\*\*Supabase \`push_subscriptions\` Table\*\*** | Stores user device subscriptions (\`user_id\`, \`endpoint\`, \`p256dh\`, \`auth\`, \`user_agent\`, \`created_at\`) with RLS protection. |

\| **\*\*Service Worker Push Event (\`sw\.js\`)\*\*** | Listens for \`self.addEventListener('push')\` to display native OS notification tiles with app icon (\`bloub-cercle-fier-violet.png\`), vibration pattern, and deep link URL. |

\| **\*\*Service Worker Click Event\*\*** | Listens for \`self.addEventListener('notificationclick')\` to bring the PWA to focus and route directly to the relevant view (e.g. \`/budgets\` or \`/transactions\`). |

\| **\*\*Backend Trigger (Supabase Edge Function)\*\*** | Automated cron or Postgres database webhook (\`pg_net\`) triggered when a transaction exceeds 85% or 100% budget, or when a recurring bill reaches its due date. |



**### Device Support Matrix**



\* **\*\*Android (Chrome, Brave, Samsung Internet)\*\***: Full background Web Push support once permission is granted.

\* **\*\*iOS / iPadOS (Safari)\*\***: Full Web Push support (iOS 16.4+) once the user has added the PWA to their Home Screen.

\* **\*\*Desktop (Chrome, Edge, Safari, Firefox)\*\***: Native OS desktop push notifications.

**# 14. Security & Rate Limiting**



Given this application stores sensitive financial data, security should be treated as a core requirement from the start rather than something layered on at the end.



**## Rate Limiting**



Rate limiting protects the system from brute-force login attempts, credential stuffing, spam, and general abuse — especially important for a financial application.



**### Suggested Starting Points**



\| Endpoint / Action | Suggested Limit | Purpose |

\|---|---|---|

\| Login | 5 attempts / 15 min per account or IP | Prevent brute-force / credential stuffing |

\| Registration | 5 / hour per IP | Prevent bot sign-ups |

\| Password reset request | 3 / hour per email | Prevent email-bombing / abuse |

\| Transaction create/update | \~60 / min per user | Prevent spam or scripted abuse |

\| General API requests | \~100 / min per user | General abuse prevention |



These are starting recommendations, not final values — exact thresholds should be confirmed with the client (see the updated Questionnaire in Section 17).



**### Implementation Options (React + Vite + Supabase)**



\- **\*\*Supabase Auth built-in limits\*\*** — Supabase Auth already applies default rate limits to sign-up, sign-in, password reset, and OTP requests. These should be reviewed in the Supabase dashboard (Authentication → Rate Limits) rather than assumed to be sufficient on their own.

\- **\*\*Edge Functions + a store (e.g., Upstash Redis)\*\*** — for business-logic endpoints like transaction creation, a Supabase Edge Function can check and increment a per-user/IP counter within a time window before allowing the request through.

\- **\*\*Database-level throttling\*\*** — a lightweight table (see below) can track recent attempts per user/action directly in Postgres. Simpler to set up, but less performant at high scale than a dedicated store.

\- **\*\*Edge/CDN-level protection\*\*** — if deployed on Vercel, Netlify, or behind Cloudflare, platform-level rate limiting or WAF rules add a layer of defense before requests even reach the app.

\- **\*\*Frontend throttling/debouncing\*\*** — improves UX (e.g., disabling a submit button while a request is in flight) but is not itself a security control; it must be backed by server-side enforcement.



**## Additional Security Measures**



Rate limiting is one layer. The following should also be part of the security baseline:



\- **\*\*Input validation & sanitization\*\*** — validate on both the client (for UX) and the server/RLS layer (for security). Never rely on client-side validation alone.

\- **\*\*XSS prevention\*\*** — React escapes output by default; avoid \`dangerouslySetInnerHTML\`, and sanitize free-text fields (transaction notes, descriptions) before rendering.

\- **\*\*Secrets management\*\*** — the Supabase \`anon\` key is safe for client-side use; the \`service_role\` key must never be exposed in frontend code and should only be used in secure server-side contexts (e.g., Edge Functions).

\- **\*\*Session/token handling\*\*** — rely on Supabase's JWT-based sessions; confirm token storage and refresh behavior are configured securely.

\- **\*\*Account lockout\*\*** — temporarily lock or add escalating delays to accounts after repeated failed logins (works together with the login rate limit above).

\- **\*\*HTTPS everywhere\*\*** — enforced by default on Supabase and typical hosts (Vercel/Netlify); confirm there's no mixed-content or HTTP fallback path.

\- **\*\*Audit logging\*\*** — record sensitive actions (login, failed login, password change, account deletion, admin actions) for traceability.

\- **\*\*Dependency security\*\*** — run \`npm audit\` and enable automated dependency updates (e.g., Dependabot), given the Node-based stack.

\- **\*\*Least privilege\*\*** — RLS policies should stay as restrictive as possible; admin capabilities should be scoped narrowly rather than granting blanket access.

\- **\*\*CAPTCHA (optional)\*\*** — consider adding to registration, login, or password-reset forms if bot abuse becomes an issue. Not required for MVP, but straightforward to add later.

**# 20. Device Optimization, Performance & Compatibility**

## 20.1 Objective

Kuri must remain fast, readable, reliable, and battery-conscious across supported devices, including budget Android phones, tablets, and desktop computers. Device optimization is a product requirement for every feature, not a final polishing task.

The application must preserve Kuri's visual identity, subtle neumorphism, responsive layout, and mascot experience while prioritizing financial-task usability, accessibility, data integrity, and performance over decorative effects.

## 20.2 Supported Device Categories

- **Mobile:** budget and mid-range Android phones, modern Android phones, and iPhones using supported browsers.
- **Tablet:** Android tablets and iPads in portrait and landscape orientations.
- **Desktop:** Windows, macOS, and Linux devices using supported versions of Chrome, Edge, Firefox, and Safari where applicable.
- **PWA:** browser-based and installed-PWA experiences, including supported home-screen installation and offline states.
- Maintain a practical device/browser test matrix and document any known platform limitations.

## 20.3 Responsive Layout and Input

- Use a mobile-first layout and prevent unintended horizontal scrolling or clipped controls at supported viewport sizes.
- Adapt navigation to screen size: desktop sidebar, tablet-appropriate navigation, and compact mobile navigation.
- Make dashboards, transaction lists, charts, forms, dialogs, cards, and settings responsive without hiding essential financial information.
- Support portrait and landscape layouts, device safe areas, browser zoom, and increased text size.
- Aim for touch targets of approximately 44 × 44 CSS pixels for primary interactive controls, with adequate spacing between actions.
- Ensure forms remain usable with virtual keyboards, browser autofill, password managers, and touch input.
- Keep primary actions such as adding a transaction, selecting an account, and saving a budget easy to reach on small screens.

## 20.4 Performance and Rendering

- Split code by route and load nonessential screens, charts, and heavy components only when needed.
- Avoid unnecessary component renders and expensive calculations; use memoization only where profiling or clear data-flow needs justify it.
- Paginate or progressively load long transaction histories instead of rendering unlimited records at once.
- Debounce search and filtering where appropriate, and avoid repeated expensive work during typing or scrolling.
- Compress and size images and other assets appropriately; avoid oversized bundles and unnecessary third-party dependencies.
- Prefer efficient CSS transforms and opacity for animations. Limit expensive blur, large shadows, backdrop filters, and continuously repainting effects on low-powered devices.
- Avoid unnecessary DOM size, layout thrashing, and repeated database/network requests.
- Pause nonessential animations and work when the page is hidden or components are off-screen.
- Validate performance using production builds and realistic datasets, not only development mode or empty screens.

## 20.5 Kuri Mascot Performance Modes

Kuri's mascot experience must adapt to user preference and device capability without blocking core finance tasks.

- **Full mode:** the complete intended animation and effects on devices that can handle them smoothly.
- **Balanced mode:** reduced particles, glow, blur, and animation frequency while retaining Kuri's recognizable expressions.
- **Lite mode:** lightweight SVG or static poses with minimal effects for constrained devices or users who prefer fewer animations.
- **Reduced motion:** respect the operating system's `prefers-reduced-motion` setting and provide an in-app preference where practical.
- Pause decorative animation when Kuri is off-screen or the page is hidden; prevent duplicate animation loops and unnecessary background work.
- Prefer lightweight SVG/CSS animation for ordinary mascot states. Use Canvas only where there is a demonstrated benefit and it can be safely paused or reduced.
- Sound and haptic feedback must be optional, respect user/device settings, and degrade gracefully when unsupported.
- Mascot effects must never delay authentication, transaction entry, saving, navigation, or other essential financial actions.
- Do not promise a fixed frame rate on every device. Target smooth animation on capable hardware and degrade gracefully on constrained hardware.

## 20.6 Network, Loading, and Offline Behavior

- Keep the initial application download small and defer nonessential assets and features.
- Use the PWA service worker to cache appropriate static application resources and support a clear offline experience.
- Provide explicit loading, empty, error, offline, and retry states for relevant screens and operations.
- Clearly distinguish locally entered, pending, saved, and successfully synchronized data. Never show a successful save or sync state until the operation is confirmed.
- Retry interrupted requests safely. For financial writes, prevent duplicate transactions and make synchronization behavior deliberate, authenticated, and idempotent where applicable.
- Do not indiscriminately cache sensitive financial responses or user-specific data. Cache policies must account for privacy, authentication, and logout behavior.
- When the network is unavailable, explain which features are unavailable and preserve only data that can be stored safely and reliably.

## 20.7 Accessibility and Usability

- Support keyboard navigation, visible focus, screen readers, and appropriate accessible names for controls.
- Maintain readable text, sufficient contrast, and layouts that remain usable when text is enlarged.
- Never communicate financial status through color alone; combine color with text, icons, or other clear indicators.
- Do not rely on hover-only interactions. Essential controls must work with touch, mouse, and keyboard as appropriate.
- Provide text summaries or accessible alternatives for charts and visual reports.
- Respect reduced-motion preferences and provide controls for optional sound and haptics.

## 20.8 Performance Targets and Measurement

Use the following as initial targets, then validate and adjust them using real production measurements:

- **Largest Contentful Paint (LCP):** 2.5 seconds or less.
- **Interaction to Next Paint (INP):** 200 milliseconds or less.
- **Cumulative Layout Shift (CLS):** 0.1 or less.
- Assess these metrics at the 75th percentile where sufficient real-user data is available, and segment results by device class and connection quality when possible.
- Prioritize time-to-usable for authentication, navigation, account selection, transaction entry, and saving financial changes.
- Aim for smooth animations on capable devices while allowing reduced effects and lower animation rates on constrained devices.
- Treat these values as goals to measure, not guarantees. Do not claim compliance without test or production evidence.

## 20.9 Device and Network QA Matrix

Test critical flows on representative combinations of:

- Low-end and mid-range Android devices.
- A modern Android device and an iPhone.
- An Android tablet and an iPad where supported.
- Desktop browsers listed in the project's supported-browser policy.
- Narrow viewports, landscape mode, high-DPI screens, browser zoom, and larger text settings.
- Fast, slow, intermittent, and offline network conditions.
- Reduced-motion settings, keyboard-only navigation, and screen-reader use for key flows.

At minimum, test authentication, onboarding, account/wallet creation, adding and editing transactions, transfers, budgets, dashboard/report views, and notification preferences. Verify that interrupted requests do not create duplicate financial records or misrepresent saved balances.

## 20.10 Definition of Done for Device Optimization

A feature that affects the interface or data flow is complete only when:

- It works at supported mobile, tablet, and desktop viewport sizes without unintended overflow.
- Primary controls are usable with supported input methods and remain accessible when text is enlarged.
- Loading, empty, error, retry, and relevant offline states are handled.
- Nonessential animation respects reduced-motion preferences and does not block core tasks.
- Performance has been checked on representative hardware using realistic data when the feature could materially affect it.
- Slow or interrupted network conditions do not cause duplicate writes, corrupted balances, or false success states.
- No avoidable performance regression or critical console error remains, and the relevant acceptance tests pass.

1\. **\*\*Welcome Page (\`/welcome\`) — The Welcoming Guide & Co-Pilot\*\***:

   - Replace the generic wallet glyph in the hero header with an animated Kuri avatar (\`mood="wave"\`).

   - In the slide deck, replace generic flat vectors with contextual Kuri feature illustrations:

     - *\*Slide 1 (Smart Tracking)\**: Kuri with a mini digital balance sheet, scanning GCash/Maya wallets.

     - *\*Slide 2 (Vault Security)\**: Kuri buffing his gold combination dial (\`mood="dial_buff"\`).

     - *\*Slide 3 (Budget Progress)\**: Kuri celebrating with floating ₱ coins (\`mood="celebrate"\`).

   - Tapping Kuri triggers friendly Philippine financial tips (*\*"Smart, not kuripot!"\**).



2\. **\*\*Login Page (\`/login\`) — The Interactive "Privacy Shield" Guard\*\***:

   - Position Kuri sitting neatly atop the login card (\~72–80px height).

   - **\*\*Email Focus\*\***: Kuri tilts head with curious cyan eyes (\`thinking\`), subtly following user keystrokes.

   - **\*\*Password Focus (Privacy Shield Mode)\*\***: Kuri covers his eyes with his safe hands (or drops a protective security shutter over his visor): *\*"Shh! Password is safe with the vault!"\**

   - **\*\*Show Password Toggle\*\***: Kuri peeks playfully through his fingers or opens one eye.

   - **\*\*Form Submitting\*\***: Antenna pulses with affirmative cyan/green light.

   - **\*\*Account Lockout / Cooldown Active\*\***: Kuri enters \`alert\` mode (amber/red visor, protective shield lowered) reinforcing security: *\*"Vault lockdown active to keep your account safe."\**



3\. **\*\*Register Page (\`/register\`) — The Onboarding Coach\*\***:

   - **\*\*Password Strength Feedback\*\***: Kuri reacts to password strength (slanted concerned brow for weak passwords ➔ energetic nod and green antenna glow for strong passwords).

   - **\*\*Password Match\*\***: Twinkle eye glint when passwords match.

   - **\*\*Success State ("Check your email")\*\***: Full celebratory hydraulic leap (\`mood="celebrate"\`) with star/confetti particles.



4\. **\*\*Performance & UX Constraints\*\***:

   - **\*\*Zero Latency\*\***: Powered exclusively by lightweight SVG vector components (\`VaultyRobot\`), avoiding canvas loops on sensitive auth forms.

   - **\*\*Unobstructed Autofill\*\***: Must not interfere with browser password managers (1Password, Bitwarden, iCloud Keychain, Chrome).

   - **\*\*Discreet Sound\*\***: Audio synthesis remains muted by default on login/register to respect quiet environments.
